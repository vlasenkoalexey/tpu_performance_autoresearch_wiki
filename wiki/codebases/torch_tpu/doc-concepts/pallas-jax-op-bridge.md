# Pallas kernels as PyTorch custom ops (torch.tpu.pallas.jax_op)

## Definition
The Pallas docs present `torch.tpu.pallas.jax_op(name, jax_fn)` as "the primary way to define a custom TPU kernel": the user writes a Pallas kernel (refs into VMEM, `x_ref[...]` loads/stores), wraps it in a plain JAX function around `pl.pallas_call(..., out_shape=jax.ShapeDtypeStruct(...))`, and `jax_op` turns that JAX function into a `torch.library.custom_op` (a `CustomOpDef`) that is called on `"tpu"` tensors like any PyTorch function. Multiple outputs are a list of `ShapeDtypeStruct`s; the op name must be namespaced (`"pallas::add_vectors"`). JAX must be installed; the rest of the model stays pure PyTorch.

## In torch_tpu (grounded)
The public symbol `torch.tpu.pallas.jax_op` resolves (through the lazy `torch.tpu` namespace built by [`install`](../catalog/src/torch_tpu/_internal/public_api.md#install) from its `ModuleSpec` table) to [`jax_op`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#jax_op), which is marked experimental.

- **Registration.** [`jax_op.dec`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#jax_op.dec "src/torch_tpu/_internal/pallas/pallas.py:L1619") validates the namespaced name, inspects the JAX function's signature ([`_verify_signature`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#_verify_signature "src/torch_tpu/_internal/pallas/pallas.py:L498")), infers which parameters are static (non-tensor) via [`_infer_static_argnums`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#_infer_static_argnums "src/torch_tpu/_internal/pallas/pallas.py:L591") / [`_infer_static_argnames`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#_infer_static_argnames "src/torch_tpu/_internal/pallas/pallas.py:L612"), builds a Torch schema with [`_generate_torch_schema`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#_generate_torch_schema "src/torch_tpu/_internal/pallas/pallas.py:L897"), and wraps a `jax.jit` of the function in a [`JaxCallable`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#JaxCallable "src/torch_tpu/_internal/pallas/pallas.py:L930") (via the deprecated-but-internal [`custom_jax_kernel`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#custom_jax_kernel "src/torch_tpu/_internal/pallas/pallas.py:L1399")). It registers the result with `torch.library.custom_op` (`mutates_args=()`) and re-classes it as [`_JaxCustomOpDef`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#_JaxCustomOpDef).
- **Automatic fake kernel.** The doc's claim that `jax_op` "handles the `register_fake` implementation internally" is [`jax_op.dec.fake_fn`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#jax_op.dec.fake_fn "src/torch_tpu/_internal/pallas/pallas.py:L1650"): it exports the JAX function on placeholders ([`JaxCallable._get_jax_placeholders`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#JaxCallable._get_jax_placeholders "src/torch_tpu/_internal/pallas/pallas.py:L1164")) and turns each output aval into a Torch placeholder with [`torch_placeholder`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#torch_placeholder "src/torch_tpu/_internal/pallas/pallas.py:L220"). It explicitly rejects tensors with symbolic (`SymInt`) dimensions - output shapes must be static unless the user overrides the fake.
- **Eager call path.** [`JaxCallable.__call__`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#JaxCallable.__call__ "src/torch_tpu/_internal/pallas/pallas.py:L1198") computes a per-invocation key ([`_get_kernel_invocation_key`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#_get_kernel_invocation_key "src/torch_tpu/_internal/pallas/pallas.py:L290")) from the trace key, argument shapes and static args. On a miss it exports the JAX function to StableHLO, strips location debug info, fingerprints the normalized MLIR with BLAKE2 ([`JaxCallable.kernel_key_to_mlir_fingerprint`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#JaxCallable.kernel_key_to_mlir_fingerprint "src/torch_tpu/_internal/pallas/pallas.py:L1006")) and registers the serialized module in the C++ registry ([`RegisterCustomKernel`](../catalog/csrc/ops/custom_kernels.cc.md#RegisterCustomKernel)). Every call then goes through the TPU op dispatcher ([`DispatchOp`](../catalog/csrc/eager/op_dispatcher.h.md#DispatchOp "csrc/eager/op_dispatcher.h:L312")) whose MLIR builder inlines the registered kernel via [`CallCustomKernel`](../catalog/csrc/ops/custom_kernels.cc.md#CallCustomKernel) - so a Pallas kernel becomes one more deferred op in the eager graph, not a separate launch path.
- **Donation and distribution.** `donate_argnums` is forwarded as donated buffer indices (donated inputs are left invalid; [`JaxCallable._donate_argnums_set`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#JaxCallable._donate_argnums_set "src/torch_tpu/_internal/pallas/pallas.py:L1068")). For cross-device kernels a `mesh` plus input/output partition specs can be passed; [`get_pallas_mesh`](../catalog/src/torch_tpu/_internal/pallas/mesh.md#get_pallas_mesh) (public `torch.tpu.pallas.get_pallas_mesh`) builds a rank-aligned `jax.sharding.Mesh` from the process group's device assignment, and [`_validate_pallas_mesh_world_size`](../catalog/src/torch_tpu/_internal/pallas/pallas.md#_validate_pallas_mesh_world_size "src/torch_tpu/_internal/pallas/pallas.py:L1366") checks it against the world size.

## Why it matters / when it applies
- **torch.compile.** Because the result is a real custom op with a fake kernel, `torch.compile(backend="tpu")` can trace it into a larger graph ("full graph fusion with custom kernels" in the doc's summary) without graph breaks; see [torch-compile-backend](../concepts/torch-compile-backend.md).
- **Autograd is manual.** For training, the doc requires defining the backward kernel with a second `jax_op` and attaching it via `CustomOpDef.register_autograd(backward, setup_context=...)`; both directions must be `jax_op`s so AOTAutograd can trace forward and backward graphs through their fake kernels. The doc example also calls `register_fake` explicitly on the backward op (overriding the generated one).
- **Compile cost and cache sharing.** Re-tracing happens per distinct (shapes, static args) combination; the MLIR fingerprint (not the process-local Python function id) is what reaches the compilation cache, so identical kernels share compiled executables across processes ([compilation-cache](../concepts/compilation-cache.md), [compilation-cache-key](../concepts/compilation-cache-key.md)).
- **Static shapes.** The default fake path fails on symbolic dims; dynamic-shape workloads need a hand-written fake or to stay off `dynamic=True` (the doc's training example uses `torch.compile(dynamic=False, backend="tpu")`).
- `custom_jax_kernel` still exists for tokamax-style wrappers but warns as deprecated; new code should use `jax_op`.

## Also: plain-JAX custom ops (no Pallas)
`docs/markdown/quantized_sum.md` uses the same `jax_op` bridge with an ordinary `jax.lax` function
instead of a Pallas kernel: `jax_op("test_example::popcount", jax_popcount)` exposes
`jax.lax.population_count`, which lowers 1:1 to StableHLO `popcnt`, an op ATen does not have. Because
`jax.lax` maps almost directly onto StableHLO, this is the Python route to any missing StableHLO op
without writing a C++ HLO kernel; `population_count` is non-differentiable, so such ops are
inference-only unless a backward is supplied (the doc points to `test_jax_dot_grad_for_backwards()`,
which derives it with `jax.jvp` / `jax.grad`). Worked example:
[one-bit-quantized-sum](one-bit-quantized-sum.md).
