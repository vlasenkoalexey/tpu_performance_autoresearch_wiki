# Launching multi-core training (torch.tpu.distributed env + torchrun + tpu_dist DDP)

## Definition
The distributed-training doc frames TorchTPU scaling as SPMD over standard PyTorch tooling: one process per TPU core, launched by `torchrun`, each process seeing only its own core as `tpu:0`, and DDP wrapping the model without `device_ids`. The TPU-specific part is a one-line bootstrap that must run *before* `torchrun` spawns workers: `eval $(python -m torch.tpu.distributed | sed 's/^/export /')`, which defines the hardware topology and slicebuilder ports. Inside the worker, `torch.device("tpu")` registers the backend and `dist.init_process_group(backend="tpu_dist")` creates the TPU process group.

## In torch_tpu (grounded)
- **The bootstrap module.** `python -m torch.tpu.distributed` is delegated by the public namespace (`main=` in the `torch.tpu.distributed` `ModuleSpec`, see [`install`](../catalog/src/torch_tpu/_internal/public_api.md#install)) to [`distributed`](../catalog/src/torch_tpu/_internal/distributed/distributed.md), whose `__main__` prints shell assignments for `TORCH_TPU_TOPOLOGY`, `TORCH_TPU_SLICEBUILDER_ADDRESSES`, `TORCH_TPU_XPROF_SESSION_ID`, `WORLD_SIZE`, `NODE_RANK` and (multi-host) `NNODES`/`MASTER_ADDR`/`MASTER_PORT` after calling [`set_tpu_launch_env`](../catalog/src/torch_tpu/_internal/distributed/distributed.md#set_tpu_launch_env). The same function is public as `torch.tpu.distributed.set_tpu_launch_env` for in-Python launchers (`torch.multiprocessing.spawn`, `elastic_launch`).
- **What it decides.** `set_tpu_launch_env` only mutates `os.environ`, never overwrites a pre-set variable, and is idempotent. Single-host: one `localhost:<free port>` slicebuilder address per device and a topology from [`get_tpu_topology`](../catalog/src/torch_tpu/_internal/utils/hardware.md#get_tpu_topology); multi-host (two or more `TPU_WORKER_HOSTNAMES`, or `JOB_COMPLETION_INDEX`): `<host>:<TORCH_TPU_BASE_PORT + i>` across all hosts (`TORCH_TPU_DEVICES_PER_HOST`, default device count or 8) and a `NODE_RANK` ranked by physical host coordinates ([`_calculate_topological_node_rank`](../catalog/src/torch_tpu/_internal/distributed/distributed.md#_calculate_topological_node_rank)) when an external `TORCH_TPU_TOPOLOGY` is supplied. The device-coordinate query runs in a child process so the parent does not claim the TPUs its workers need.
- **Worker side.** The C++ runtime refuses to start a distributed worker unless `RANK`, `LOCAL_RANK`, `WORLD_SIZE`, `MASTER_ADDR`, `MASTER_PORT`, `TORCH_TPU_SLICEBUILDER_ADDRESSES` and `TORCH_TPU_TOPOLOGY` are all set ([`ValidateRequiredDistributedEnvVars`](../catalog/csrc/distributed/slicebuilder/discovery.cc.md#ValidateRequiredDistributedEnvVars "csrc/distributed/slicebuilder/discovery.cc:L32")); [`GetDistributedWorkerConfiguration`](../catalog/csrc/distributed/slicebuilder/discovery.cc.md#GetDistributedWorkerConfiguration "csrc/distributed/slicebuilder/discovery.cc:L65") picks this rank's slicebuilder port from the address list into a [`DistributedWorkerConfiguration`](../catalog/csrc/distributed/slicebuilder/discovery.h.md#DistributedWorkerConfiguration "csrc/distributed/slicebuilder/discovery.h:L29"). That per-rank binding is why each process sees exactly one device and DDP needs no `device_ids`.
- **The `tpu_dist` backend.** [`register_torchcomms_tpu`](../catalog/src/torch_tpu/_internal/distributed/torchcomm_tpu.md#register_torchcomms_tpu) registers `"tpu"` and `"tpu_dist"` with `torch.distributed.Backend` (and torchcomms when present) and maps the `tpu` device to `tpu_dist` by default. The process group it creates is the C++ [`ProcessGroupTpu`](../catalog/csrc/distributed/process_group_tpu.h.md#ProcessGroupTpu "csrc/distributed/process_group_tpu.h:L134"), whose [`allreduce`](../catalog/csrc/distributed/process_group_tpu.cc.md#ProcessGroupTpu.allreduce "csrc/distributed/process_group_tpu.cc:L1785") is what DDP's gradient buckets call.

## Why it matters / when it applies
- **The bootstrap is mandatory and must precede the launcher**: every rank must agree on the same address list and topology, which is why they are decided once in the parent. Missing it surfaces as the "missing required environment variables" precondition error, or as a rendezvous hang for multi-host mismatches (`nnodes` is cross-checked against `TPU_WORKER_HOSTNAMES` to fail fast instead).
- `torchrun --nproc_per_node=$WORLD_SIZE` with the exported `WORLD_SIZE` is the canonical single-host form; the doc's model and data are cast to `bfloat16` so DDP gradient all-reduces run in bf16 ([dtype-and-precision](../concepts/dtype-and-precision.md)).
- The doc ends the step with `loss.item()` as a "mandatory materialization trigger" that keeps ranks in lock-step - see [spmd-lockstep-and-collective-fusion](spmd-lockstep-and-collective-fusion.md) for why that sync point and rank-divergent code interact.
- Distributed code cannot run inside a notebook kernel; it needs a real launcher process.
