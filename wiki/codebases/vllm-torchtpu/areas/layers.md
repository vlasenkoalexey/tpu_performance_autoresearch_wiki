# Area: `src/vllm_torchtpu/layers`

## Purpose
Upstream vLLM model code is written against torch modules and vLLM extension points: `AttentionBackend`, `QuantizationConfig`, the fused-MoE runner and the sampler. This area makes those extension points run on TPU kernels without forking the models. Two layers do the work. [attention-and-layer-core](../concepts/attention-and-layer-core.md) (`layers/core`) is the JAX side. It owns the one fixed-shape `AttentionMetadata` pytree that every attention-like kernel consumes, the builder that fills it once per runner chunk, sequence-layout planners for prefill context parallelism, and thin `shard_map` wrappers that place each kernel from [kernels](kernels.md) on the device mesh. [vllm-layer-adapters](../concepts/vllm-layer-adapters.md) (`layers/adapter`) is the torch side. It registers a Pallas attention backend in vLLM's attention slots, hands out TPU linear and MoE methods, and arms optional fused MoE kernels after load.

The design idea that governs the whole area is to resolve everything before tracing. Kernels are built and registered as torch custom ops, weights are converted to their runtime layout at load time, and kernel choices are fixed once. The per-step forward that torch.compile captures is then only calls into already-built ops. This is what lets the [model runner](../concepts/tpu-model-runner.md) AOT-compile one program per bucket while the batch changes every step.

Two units carry most of the model-format and kernel coverage: [quantization-methods](../concepts/quantization-methods.md) converts each checkpoint format (FP8 block-scaled, NVFP4, MXFP4, INT4, BF16) once at load into the layouts the matmul and GMM kernels expect, and [custom-ops](../concepts/custom-ops.md) wraps MLA, GDN/KDA, the DeepSeek-V4 compressor/indexer/mHC and the MoE runner as opaque Pallas torch ops.

## How the units connect
- [attention-and-layer-core](../concepts/attention-and-layer-core.md) is the bottom layer. Every adapter that runs a kernel goes through its metadata object and mesh wrappers.
- [vllm-layer-adapters](../concepts/vllm-layer-adapters.md) plugs into vLLM: the attention backends (`PallasAttentionBackend`, `PallasMLAttentionBackend`), linear and MoE bridges, and MoE routing/decode adapters. It calls into the core and into the two adapter sub-units.
- [quantization-methods](../concepts/quantization-methods.md) (`adapter/quantization`) supplies the quant method each linear and MoE layer gets. Its converted weights feed the quantized-matmul and megablox GMM kernels.
- [custom-ops](../concepts/custom-ops.md) (`adapter/custom_ops`) holds the layers whose math needs an opaque Pallas op. The layer adapters and the plugin's own models in [models](models.md) use them.
- `adapter/sample` (no page) holds the TPU samplers the runner builds. `top_k_top_p.py` does top-k and top-p masking by binary search over float32 bits instead of a vocabulary sort, plus a candidate-block variant that only searches the blocks with the largest maxima. `rejection_sampler.py` is a torch-based rejection sampler for [speculative-decoding](../concepts/speculative-decoding.md) verify steps, built on the same masking. With speculative decoding on and no request setting top-k or top-p, the runner skips this step on a separate compiled graph, because the full bisection costs milliseconds per verify batch.
